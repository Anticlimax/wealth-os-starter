# 从零建立个人系统

先运行演示，理解数据口径，再建立独立的 `data/personal/`。不要把演示数据换个名字当成真实账本。

## 第一次访谈

模型每次问少量问题，允许回答“不知道”。先收集以下项目：

1. 本位币、主要居住地区、希望解决的规划问题；地区只用于理解币种和资料，程序不判断税务或产品准入。
2. 月收入、必要与非必要支出、债务偿还支出，数字是估计还是实际流水统计。月支出若已含还款，不要再加一次。
3. 截至同一时点的账户别名、现金、证券数量、在途款、负债本金。资产与负债分开，避免同一资产在两个账户重复出现。
4. 已有应急资金、希望覆盖的支出月数、未来一至三年的目标及目标优先级。
5. 对波动和资金可用性的约束。先澄清这些信息，再讨论配置；演示比例不具有推荐意义。

不要求提供账号、完整姓名、身份证、地址、密码或交易权限。凭证可留在本地 `private/`，事件引用本地别名即可。模型使用哪些数据由用户决定。

## 整理草案

初始化后，在 `data/personal/drafts/` 整理可核对表格：字段、数值、币种、日期、来源、未知项。不要把草案写进 examples/ 或 docs/。

- `profile.json`：本位币、月收支估计、应急月数、账户及资产字典。
- `opening.json`：统一期初时点及持仓数量，负债数量使用正值，资产 kind 标记 liability。用户确认后设 `confirmed: true`。
- `prices.json`：每项价格与汇率的日期和来源。现金和以金额记账的债务也显式填写单价 1；不隐式填入缺失市场价格。
- `plan.json`：配置目标与资金目标，默认 draft。确认计划只改变计划状态，不改变账本。
- `events.jsonl`：期初之后的实际变动；没有记录就保持空文件。

在已有账本开始记录事件后，期初应保持不变。若期初本身有错，先备份，核对影响，再采用有凭证的 adjustment 更正或制定明确的迁移方案；不要悄悄重置。

## 让用户核对

列出资产负债总额、缺估值项、期初时点、月结余、应急缺口、目标月投入。明确哪些是原始记录、哪些是用户估计、哪些是模型草案。缺数据时，总资产和净资产可能为未知；已知小计不能冒充完整总额。

确认后运行 validate、report、serve，打开页面核对。资产、负债和净资产应与用户确认的口径一致。未对账差额保留为待核对，不擅自加 adjustment 抹平。

## 日常节奏

- 实际发生后记账：收入、支出、买卖、划转、申购、结算和费用。
- 价格更新后：写入来源与日期，运行 validate，然后刷新页面。
- 每月：与真实余额对账，更新月收支估计，检查目标资金是否重复使用，做一次摘要。
- 自动化是后续可选扩展。先跑通手动流程，再由用户决定数据源、运行位置和通知方式。

若需要保存原始单据，放在 private/ 或 data/personal/evidence/。若使用云端模型，是否向其提供私密资料取决于你选用的服务和设置；本项目自身不调用模型服务。
